# Task Plan: task0002 — Semver-greatest persisted baseline and parseable-only latest selection

## Goal

The pipeline persists the semver-greatest tag name among the releases it just
delivered, the latest-release query refuses to select a tag that does not
parse, and both reach the comparison rule through a single exported entry
point in the release package — so the value this tool stores always satisfies
the parsing rule its own read path requires.

## Requirements

FR7, FR9, FR10, NFR4

## Scope

### Files to Create
- `internal/app/app_test.go` — the pipeline's first test file; mocks the five
  leaf roles at the consumer-side interfaces and covers the persisted-baseline
  behaviour

### Files to Modify
- `internal/github/client.go` — add the exported semver-maximum selector; narrow

- `internal/github/client_test.go` — add the selector's table-driven test and

- `internal/app/app.go` — persist the selected maximum instead of the delivered

## Design

The three contracts this task implements are pinned in IMPLEMENTATION.md
Shared Components and are not restated here: the exported semver-maximum
selector, the revised latest-release query, and the pipeline's
persisted-baseline decision. The conventions under "Go changes" apply in full,
in particular the ban on any new exported identifier beyond the selector and
on any second parsing or comparison site.

### The four changes

1. **The selector (NFR4).** A package-level pure function in the release
   package, taking the delivered releases and returning the one whose tag name
   is the greatest parsed version, together with a found flag. It reuses the
   package's existing unexported parse and compare helpers; those helpers stay
   unexported and are not modified. It performs no I/O, and it neither sorts
   nor otherwise reorders the slice it is given.

2. **The latest-release query (FR10).** Its existing skip conditions — draft
   and prerelease — gain one more: a tag name that does not parse. The
   selection is otherwise unchanged, and so is the pagination walk and the
   error raised when the walk ends with nothing selected. Concretely this makes
   the query's filter the same one the differential query already applies, so
   the two paths agree on what a deliverable release is.

3. **The persisted baseline (FR9).** After a successful send, the pipeline
   currently takes the first element of the delivered slice. It instead asks
   the selector for the maximum of that slice and persists that release's tag
   name. Everything around it is unchanged: the save still happens only after
   a successful send, nothing is persisted when nothing was delivered (the
   pipeline already returns early on an empty set), and the slice handed to
   the mail builder keeps its listing order. If the selector reports nothing
   found — unreachable given the two query contracts — the pipeline surfaces
   it the way it already surfaces a store failure: a state-stage error after
   the send, with the stored value left untouched.

4. **The doc comment (FR7).** The differential method's doc comment on the
   pipeline's release-fetcher abstraction must state three things: that
   newness is decided by semantic-version comparison of tag names, that the
   query is bounded to a single listing page, and that an empty result means
   "already up to date". It currently carries the last two and omits the
   first. Only the missing statement is added; the comment is not rewritten
   wholesale.

### Where the new pipeline test sits

The pipeline package has no test file today. The new one mocks the five leaf
roles through the consumer-side interfaces the package already declares —
that is the established mocking seam and no production code changes to
accommodate testing. The stages this task does not care about (configuration,
translation, mail build, mail send) are stubbed to succeed; the state store
mock records the value it is asked to save so the assertion can read it.

## Acceptance Criteria (MANDATORY)

- [ ] AC-1 (NFR4, TS-16): The exported selector exists with the pinned
      contract and is covered by a table-driven test whose cases include the
      maximum at the head, the maximum at the tail, a single element, two
      inputs with equal versions (the earlier one wins), an input whose tag
      does not parse being ignored, and an empty input reporting nothing
      found. The function performs no I/O and leaves its input's order
      unchanged.
- [ ] AC-2 (FR10, TS-14): Given a listing whose head is a non-draft,
      non-prerelease release with an unparseable tag, the latest-release query
      returns the next parseable release instead. Given a listing with no
      parseable, non-draft, non-prerelease entry at all, it returns the
      existing "no releases found" error. Its pagination walk is unchanged.
- [ ] AC-3 (FR9, TS-13): In a pipeline run where the differential query
      returns a set whose head is not its semver maximum — the specification's
      example of two releases at versions 2.1.244 and 2.2.0, in that listing
      order, against a stored 2.0.0 — the value the state store receives is
      the 2.2.0 tag name, and the items handed to the mail builder are still
      in the order the query returned.
- [ ] AC-4 (FR9): A run that delivers nothing saves nothing, and a run whose
      send fails saves nothing — both verified against the state store mock's
      recorded calls.
- [ ] AC-5 (NFR4, TS-16, AC-13): The pipeline package contains no
      `vMAJOR.MINOR.PATCH` parsing and no version comparison of its own, in
      production code or in the new test file; it reaches the rule through
      exactly one call site into the exported selector. The release package's
      version type and its parse and compare helpers are still unexported.
- [ ] AC-6 (FR7, TS-11): The differential method's doc comment on the
      release-fetcher abstraction states semver comparison, single-page
      boundedness, and that an empty result means "already up to date".
- [ ] AC-7: The build command, the full test command, the format command and
      the Go vet check all pass with no change left in the working tree, and
      the module's require block is byte-identical to its pre-task state (no
      dependency added, NFR1).

## Test Notes

Written test-first, in the order the criteria are numbered — the selector's
table before the selector, the two latest-release cases before the skip
condition, the pipeline case before the persisted-value change.

- AC-1 and AC-2 are unit tests in the release package's existing test file,
  alongside the tests already there. AC-2 reuses that file's existing local
  HTTP test-server pattern with canned listing JSON; no new test helper style
  is introduced.
- AC-3 and AC-4 are the new pipeline test file. They are integration-flavoured
  in that they drive the whole run, but they use only in-process mocks: no
  network, no subprocess, no SMTP.
- AC-5's first half is a textual check of the pipeline package's source, not a
  Go test (IMPLEMENTATION.md D9): search it for digit-splitting, dot-splitting
  or comparison of version components, expecting no hit, and count the call
  sites into the selector, expecting exactly one. Its second half is satisfied
  by the release package's identifiers remaining lowercase-initial.
- AC-6 is a read-through, not a test.
- Edge cases worth covering beyond the criteria: a delivered set of exactly
  one release (the maximum is that release), and a listing whose only
  parseable entries are drafts or prereleases (the latest-release query must
  still reach its no-candidate error rather than returning a filtered entry).
- TDD-awkward: AC-6 is prose and has no red-green cycle; it is verified by
  reading the comment against its three required statements.

## Out of Scope

- The differential query's own behaviour: its comparison rule, its
  single-page boundedness, the per-page constant, its error for an unparseable
  stored version, and its draft and prerelease filtering are already
  implemented and confirmed, and no line of them changes here.
- The latest-release query's pagination walk, its request construction, and
  its headers.
- The save timing (after a successful send only), the state file's format, and
  the atomic-write mechanism.
- Translation, mail building, mail sending, and configuration loading — stubbed
  in the new test, never modified.
- Every document under `feature-docs/release-notes-fetcher/`: those belong to
  the documentation task and are not touched here.
- Adding a dependency, adding an exported identifier other than the selector,
  and exporting any existing helper.
