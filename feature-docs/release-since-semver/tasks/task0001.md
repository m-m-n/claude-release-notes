## Goal

The sixteen stale locations in `feature-docs/release-notes-fetcher/` describe
the behaviour the code actually has today, so that reading those documents no
longer produces the paging-based or identity-match-based understanding.

## Design

All work is prose editing. The behaviour being described is fixed and is
stated once in IMPLEMENTATION.md as the current-behaviour reference and the
canonical statements CB1–CB8; this plan does not restate it. The conventions
that govern how the edits are made (minimal edit, language preservation,
terminology, historical records untouched) are also IMPLEMENTATION.md's and
apply in full.

### Target locations

Each row names a location by its heading and the text that identifies it
today, and states what the location must convey afterwards by canonical
statement. Wording is the implementer's, within the terminology convention.

## Test Notes

There is no documentation-test harness in this project and none is added
(IMPLEMENTATION.md D3). Verification of every criterion is textual and
repeatable:

- AC-1 through AC-3 and AC-7: read each of the sixteen locations against its
  row in the target-location table and confirm the listed canonical statements are
  present and nothing else in the section changed.
- AC-4: a case-insensitive search of the four files for the stale-marker set,
  expected to return no hit. Run it over the whole file, not only the target
  locations, so that a duplicated stale sentence elsewhere in a target file is
  caught.
- AC-5: confirm the named out-of-scope statements are absent from the diff.
- AC-6: review the diff's file list.

TDD-awkward: prose has no red-green cycle. The handling is that AC-4 is a
mechanical check that can be run BEFORE the edits (expected to fail, listing
each stale marker's location) and after (expected to be empty), which gives
the same before/after evidence a test would.
