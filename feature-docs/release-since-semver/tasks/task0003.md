# Task Plan: task0003 — Align legacy docs with the semver-greatest baseline and parseable-only latest selection

## Goal

The twenty statements in `feature-docs/release-notes-fetcher/` that FR9 and
FR10 make stale describe the behaviour the code has after this feature, so
that reading those documents no longer produces the "the stored value is the
head of the listing" or "the latest-release query unconditionally takes the
head" understanding.

FR11

## Design

All work is prose editing. The behaviour being described is fixed and is
stated once in IMPLEMENTATION.md as the current-behaviour reference and the
canonical statements CB1–CB10; this plan does not restate it. The conventions
that govern how the edits are made — minimal edit, language preservation,
terminology, no implementation detail, historical records untouched,
still-true statements left alone — are IMPLEMENTATION.md's and apply in full.

**A naming collision to keep straight**: one of the files being edited is
`feature-docs/release-notes-fetcher/tasks/task0003.md`, a task plan belonging
to a different, older feature. It is not this plan. Every reference below
that means the older file gives its full path; the bare name never appears.

Two canonical statements carry this task:

- **CB9** for statements about what gets stored after a successful send.
- **CB10** for statements about how the latest-release query picks its result.

### Boundary the task must not cross

- **The sixteen locations task0001 already rewrote are not rewritten again.**
  This task's set is disjoint from them at statement granularity
  (IMPLEMENTATION.md D8). Where a target sits inside a section task0001 also
  edited — L10 inside the fetch-feature description, L6 and L8 inside the use
  cases — only the sentence named in the table changes.
- **Two of task0001's preserved-statement boundaries are deliberately
  superseded, and only those two**: L15 (task0001 AC-7) and L19's selection
  rule (task0001 AC-5). Everything else task0001 preserved stays preserved,
  including the pagination wording in the older
  `feature-docs/release-notes-fetcher/tasks/task0003.md` under Files to Create
  and in that file's Test Notes.
- **Statements about save timing and the atomic write are current**, not
  stale: the save still happens only after a successful send and still uses
  the temp-file-and-rename mechanism. FR9 changes the value, not the timing or
  the mechanism.
- **The first-run use case's recording step** (`3.2 UC02 基本フロー` step 4)
  records the version of the single release step 2 selected; once L8 is
  corrected, that step is accurate and is not a target.
- **The narrative sentence of US2** in
  `feature-docs/release-notes-fetcher/SPEC.md` states the owner's intent (not
  receiving a backlog), not a behavioural rule, and is not a target; only its
  acceptance criterion (L3) is.
- **Historical records** — anything under
  `feature-docs/release-notes-fetcher/reviews/` or `phase-state/` — are never
  rewritten, even where they describe the older behaviour.

## Test Notes

There is no documentation-test harness in this project and none is added
(IMPLEMENTATION.md D3). Verification of every criterion is textual and
repeatable:

- AC-1 through AC-4: read each of the twenty locations against its row in the
  target-location table and confirm the listed canonical statements are
  present and nothing else in the section changed.
- AC-5: a case-insensitive search of the four files for the stale-marker set,
  expected to return no hit. Run it over each whole file, not only the target
  locations, so that a duplicated stale sentence elsewhere in a target file is
  caught. Expect the Japanese markers to need reading in context rather than a
  literal match, because 最新 is a legitimate word elsewhere in those
  documents — for example in the mail-ordering requirement, which is about
  display order and is not a target.
- AC-6 and AC-7: review the diff — its file list for AC-7, and its hunks
  against task0001's target-location table and preserved-statement criteria
  for AC-6.

TDD-awkward: prose has no red-green cycle. The handling is that AC-5 is a
mechanical check that can be run BEFORE the edits (expected to fail, listing
each stale marker's location) and after (expected to be empty), which gives
the same before-and-after evidence a test would.
