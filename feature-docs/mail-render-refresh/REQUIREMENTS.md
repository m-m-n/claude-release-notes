# メール本文の Markdown レンダリングと寒色デザイン反映 - 要件定義書

## 1. 概要

### 1.1 背景
release-notes-fetcher の初回実運用で 2 点の課題が確認された:

1. リリースノート本文が Markdown 記法（`## 見出し`・`- 箇条書き`・
   バッククォート等）のまま生テキストとして表示される
2. `/em-workflow:design` でデザイントークンが寒色ベースに更新されたが、
   実装のインラインスタイルは旧暖色のまま

### 1.2 目的
メール本文の Markdown を HTML として描画し、現行デザイントークン（寒色）を
実装に反映する。

### 1.3 スコープ
- `internal/mail` の HTML 構築（Markdown レンダラ追加・配色更新）
- `internal/translate` の翻訳指示（Markdown 構造の保持を明示）
- スコープ外: メール以外の出力、取得・送信・状態管理のロジック変更、
  外部 Markdown ライブラリの導入

## 2. ビジネス要件

### 2.1 ビジネス目標
届いたメールが整形済みで読みやすい状態にする。

### 2.2 対象ユーザー
| ユーザータイプ | 説明 |
|----------------|------|
| 本人（単一ユーザー） | 配信されたメールを読む |

### 2.3 期待される効果
- リリースノートの可読性向上

## 3. ユースケース

### 3.1 ユースケース一覧
| ID | ユースケース名 | アクター | 優先度 |
|----|----------------|----------|--------|
| UC01 | Markdown 整形済みメールの受信 | systemd timer | 高 |

### 3.2 ユースケース詳細

#### UC01: Markdown 整形済みメールの受信

**基本フロー**:
1. 定期実行で新規リリースを取得・翻訳する（既存フロー）
2. 翻訳済み本文の Markdown が HTML 要素として描画される
3. 寒色パレットのメールが届く

## 4. 機能要件

### 4.1 機能一覧
| ID | 機能名 | 説明 | 優先度 |
|----|--------|------|--------|
| F01 | Markdown レンダリング | 本文の Markdown を HTML 要素へ変換 | 高 |
| F02 | 寒色デザイン反映 | tokens.yaml の現行値をインラインスタイルへ反映 | 高 |
| F03 | 翻訳時の Markdown 保持 | 翻訳指示に Markdown 構造の保持を明示 | 中 |

### 4.2 機能詳細

#### F01: Markdown レンダリング

**説明**: 自前の最小レンダラ（標準ライブラリのみ）で以下を変換する。

| 記法 | 出力 |
|------|------|
| `#`〜`###` 見出し | メール内サブ見出し |
| `- ` / `* ` 箇条書き | 箇条書きリスト |
| `1. ` 番号リスト | 番号付きリスト |
| `` `code` `` | インラインコード |
| `**太字**` | 強調 |
| `[text](url)` | リンク（http/https のみ） |
| ` ``` ` コードブロック | 整形済みブロック |

**ビジネスルール**:
- 未対応記法・パース不能な行はプレーンな段落として表示する（欠落させない）
- すべてのテキストはエスケープ後にマークアップする（生 HTML は通さない）

#### F02: 寒色デザイン反映

**説明**: `design-system/tokens.yaml` の現行値（寒色パレット）と DESIGN.md の
Markdown 要素スタイルをインラインスタイルとして反映する。

#### F03: 翻訳時の Markdown 保持

**説明**: claude-batch への翻訳指示に「Markdown 記法・構造を原文のまま
保持する」ことを明示する。

## 5. 非機能要件

### 5.1〜5.5
- 依存方針は現状維持（標準ライブラリ + yaml.v3 のみ。レンダラは自前実装）
- セキュリティ: エスケープ後マークアップ、リンク URL は http/https のみ許可
- その他は release-notes-fetcher の非機能要件を踏襲

## 6. UI/UX要件

### 6.1 画面設計要件
Markdown 要素（サブ見出し・リスト・コード・リンク）のメール内スタイルは
design ステップで決定し、DESIGN.md に記録する。

## 7〜10. データ要件・外部連携・制約・リスク

- データ・外部連携の変更なし
- 制約: 外部 Markdown ライブラリを導入しない
- リスク: 特殊な Markdown（ネストリスト等）は簡易表示に落ちる（許容。
  プレーン段落へのフォールバックで欠落はしない）

## 11. 成功基準

### 11.1 受け入れ基準
- [ ] `## 見出し`・`- リスト`・バッククォートが HTML 要素として描画される
- [ ] 未対応記法が欠落せずプレーン表示される
- [ ] メールの配色が tokens.yaml の寒色値と一致する
- [ ] 本文経由の HTML 注入ができない（エスケープ維持）

## 12. テストシナリオ

### 12.1 テスト観点
- [ ] 正常系: 各記法の変換、配色の一致
- [ ] 異常系: 不正リンク URL（javascript: 等）の拒否、生 HTML の無害化
- [ ] 境界値: 空本文、記法なしプレーン本文、閉じられていないコードブロック

## 13. 用語定義

release-notes-fetcher の要件定義書に準ずる。
